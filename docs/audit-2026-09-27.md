# CampusFlow consistency audit — 27 September 2026

Audited commit: `0442ffc` (Add Brevo email support for Render).

## Result

The deployed frontend matches the local build, and the core application runs. The implementation does **not** fully match the discussed roadmap. Existing tests pass, but targeted checks reproduced access/visibility inconsistencies and source review identified incomplete workflows.

No application fixes, production records, production accounts, email sends, or storage uploads were made during this audit. This report is the only intended repository change. Approval is pending for remediation.

## Confirmed findings and proposed work

### 1. High — Club event visibility and registration bypass membership

Evidence: `server/src/modules/campus/campus.routes.js:17` lists all active events. Registration at line 22 checks audience eligibility but not club membership or club status. `server/src/modules/search/search.routes.js:33` likewise returns club events without membership filtering. The design's implementation Step 34 explicitly limits searched club events to accessible club spaces.

Reproduction: create an approval-required club, an event attached to its space, and a student with zero memberships. That student sees the event, finds it through search, and receives HTTP 200 when registering.

Proposed fix: centralize event visibility/access checks, enforce active club/space membership consistently for club-scoped events, and preserve campus-event audience rules. Add tests for members, nonmembers, inactive clubs and campus events. Confirm any intentional campus-wide visibility for club events before changing that policy.

### 2. High — Placement visibility differs across list, search and calendar

Evidence: `server/src/modules/campus/campus.routes.js:57` returns ineligible placements; `client/src/pages/CampusListPage.jsx:24` renders them. Search omits placement eligibility checks. Calendar does filter to eligible placements. Implementation Step 51 says proven-ineligible placements should not be shown; Step 34's search does the same except for authorized managers.

Reproduction: a student with CGPA 5 sees a placement requiring CGPA 9 in the list (labelled INELIGIBLE) and in global search. Mark-as-applied is still protected; this is a visibility/design inconsistency, not a successful application bypass.

Proposed fix: apply a shared visibility policy before limiting search/list results, with explicit manager access and UNKNOWN handling. Test all three eligibility states.

### 3. Major missing workflow — Club leaders cannot manage events

Evidence: `client/src/pages/SpacePage.jsx:45` gives club spaces overview, announcements, discussion, resources and members, but no Events tab. `server/src/modules/clubs/club.routes.js` has membership/request operations and no event-management routes. Events are created through college-admin routes. Steps 29 and 50 describe club lead/core-team event creation and a club Events tab.

Proposed fix: add club event listing/create/edit/cancel operations with contextual CLUB_LEAD/CORE_TEAM authorization, then expose them in the club workspace. Test denial for ordinary members and unrelated club leaders.

### 4. Major missing workflow — Assignment deadline changes

Evidence: `server/src/modules/spaces/content.routes.js:146` supports assignment creation, cancellation and student progress, but no assignment editing endpoint. `client/src/pages/SpacePage.jsx` has no assignment edit action. The earlier design's Step 39, workflow 6, explicitly describes deadline editing, important notifications and refreshed views.

Proposed fix: add assigned-faculty editing, deadline-change notifications, reminder rescheduling/deduplication and query invalidation. Preserve student progress and test ownership, changed deadlines and notification duplicates.

### 5. Major missing workflow — Notice closure and acknowledgement analytics

Evidence: `server/src/modules/notices/notice.model.js` has ACTIVE/REMOVED but no CLOSED state, closure metadata or `targetedRecipientCount`. `server/src/modules/admin/admin.schemas.js:19` also rejects CLOSED. The admin UI lists acknowledging users but provides no original recipient count, pending count or acknowledgement rate. Implementation Step 39 explicitly requires those fields and calculations.

Proposed fix: implement distinct closed/expired/removed behavior and snapshot the eligible audience at publication. Add acknowledgement totals/rates to admin detail. Historical notices without a snapshot must be labelled unavailable or estimated rather than given fabricated original counts.

### 6. Medium — Lost & Found missing from global search

Evidence: `server/src/modules/search/search.routes.js:17` and `client/src/pages/SearchPage.jsx` have no LOST_FOUND type; no LostFound model is searched. Step 34 includes it.

Reproduction: a matching Lost & Found record is absent from ALL results; requesting `type=LOST_FOUND` returns HTTP 400. The separate Lost & Found listing still works.

Proposed fix: add the type, model query, safe snippet and destination, while excluding removed listings. Test it through the search UI and API.

### 7. Medium — Registration hides an email-delivery failure

Evidence: `server/src/modules/auth/auth.controller.js:8` deliberately returns `emailSent:false` with an explanation when account creation succeeds but delivery fails. `client/src/pages/RegisterPage.jsx:40` discards that response and navigates to verification. `VerifyEmailPage.jsx:26` says a code was sent regardless.

Proposed fix: preserve the delivery result and show an accurate account-created/email-failed message with a resend action. Test with a mocked provider failure. This is a code-path defect; a real Brevo delivery failure was not observed during this audit.

### 8. Medium — Admin actions lack the planned confirmations

Evidence: `client/src/pages/AdminPage.jsx:44` suspends/activates users directly on click. Club membership and moderation changes submit directly as well. Implementation Step 53 calls for explicit confirmation of consequential admin actions.

Proposed fix: add accessible confirmation dialogs identifying the user/content and consequence, with pending/error states. Do not trigger live suspensions merely to test this.

### 9. Medium — Admin lists and pickers stop at 200 records

Evidence: `server/src/modules/admin/admin.routes.js:51` and `:126` limit lists to 200 with no pagination. `client/src/pages/AdminPage.jsx:18` builds all faculty/member selectors from those lists. Older users and academic records can become unavailable in the UI after growth. The roadmap discusses paginated, filterable administration.

Proposed fix: add server pagination/search and searchable relationship selectors, then test with more than 200 records. This is a demonstrated code bound, not an observed current production data-volume failure.

### 10. Medium — Calendar cache is not invalidated by workspace changes

Evidence: `client/src/pages/SpacePage.jsx:34` invalidates workspace/dashboard after actions, and `client/src/hooks/useSpaceSocket.js:13` does likewise on realtime changes. Neither invalidates calendar. `client/src/main.jsx` gives cached queries a 30-second freshness window.

Impact: a recently viewed calendar can retain stale completion or schedule state after a workspace change; an already open calendar does not subscribe to workspace changes itself. This is source-confirmed missing invalidation, not a timed browser reproduction in this pass.

Proposed fix: invalidate relevant calendar queries on assignment/schedule changes and progress updates; define cross-tab/realtime refresh behavior and test it.

### 11. Design gap requiring scope confirmation — Announcement acknowledgements

The earlier architecture's Step 39, workflow 9, describes faculty-enabled announcement acknowledgements and recipient counts. The current announcement model, routes and workspace UI have no acknowledgement capability. Campus notices do have acknowledgements. The later Step 16 implementation is narrower, so confirm whether to include the earlier workflow in the final product.

### 12. Minor/design — UI implements a simpler version of the polish roadmap

Examples: one generic campus listing replaces separate detail/filter workflows; community shows both lists rather than the planned discovery tabs/search; forms are mostly inline expandable sections rather than the planned modals; profile and settings share one page; calendar lacks the planned legend; admin uses generic sections with fewer filters and metrics. The green visual theme also differs from the indigo examples in the polish steps.

These are not all runtime bugs. Agree on the desired final screens before a visual rebuild. No original attachment-based mockup was available for a pixel comparison.

### 13. Cleanup — Documentation overstates completion and is outdated

`docs/implementation-progress.md` still says the work is uncommitted/undeployed and lists 27 backend tests. Its broad completion claim is not supported by the findings above. The current deployment and 28 passing backend tests should be recorded, with explicit incomplete workflows and provider checks.

## Remediation after “fix all” authorization

The findings above preserve the original deployed-state audit. The user subsequently authorized all fixes. Local remediation now covers findings 1–11: membership and placement filtering, club event management, faculty deadline edits, notice closure/snapshot statistics, Lost & Found search, delivery feedback, admin confirmations/pagination, calendar invalidation and announcement acknowledgements.

Finding 12: added campus details/search/filters, community tabs/search, modal content editors, separate profile/settings, calendar legend, admin role/status filters and additional metrics. Accents now follow the indigo examples. The original image mockup is unavailable, so exact visual equivalence remains unverified.

Finding 13: replaced the stale implementation record with current deployment status, test evidence and explicit limits. The baseline is live; these fixes have not been pushed/deployed.

Regression coverage: 35 backend tests and 7 client tests. Browser smoke checks used an isolated local fixture, including creating a club event, checking its detail view at 390px, and inspecting admin controls. The browser pass caught and fixed duplicate event rendering caused by two components sharing the event query cache.

Historical notices do not have a recoverable publication-time recipient snapshot; their analytics show unknown totals rather than inventing rates. New notices and acknowledgement-enabled announcements record stable target counts.

Still required after deployment: real Brevo delivery, authenticated production flows, R2 persistence across restart and multi-user production verification. No production records or secrets were changed during remediation.
